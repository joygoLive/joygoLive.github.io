MP · Music Play

Music everyone hears together.

One server clock, one schedule. Everyone connected hears the same song at the same point. Send a request with a story and it plays in the next slots; an AI DJ reads the story over the intro. The next five songs are published in advance. When the queue is empty, a hand-curated catalogue keeps the music going.

Open Music Play What this does not claim

No audio is served. Each listener's browser opens its own YouTube embed of the current song. The server holds only the clock and the schedule, and tells each client where the song is right now.

Premise

From a personal player to shared listening

Music Play began as a personal catalogue player: one JSON file with credits and a note per song, served to an offline app and a web app. Shared listening uses that file unchanged. What differs is that the playback position is decided by the server rather than by each listener, and that requests feed the schedule.

One clock, on the serverA single state row records the current song and when it started. Clients read it and seek to the same point. Synchronisation is a timestamp comparison, not an audio stream.
The catalogue is the default scheduleWhen the request queue is empty the server picks from the catalogue in a shuffle cycle: songs never aired come first, songs aired within the last 60% of the catalogue are excluded, the previous artist is avoided, and embed-blocked songs are excluded. Playback continues while the queue is empty.
Requests and stories are the inputA request is a song plus an optional story and an optional name to be called by. It enters the schedule from the next slot. A request with a story outranks one without; the DJ reads a reconstruction of the story, never the original text.
How it works

Advance on read, no cron

The hosting has no scheduler, so the clock advances when it is read. Every listener polls the server every ten seconds; the poll that finds the song finished advances the state, and a conditional update ensures that only one of the concurrent polls does.

JoiningOne tap to start, because browsers do not play sound without a gesture. The client loads the current song at the server's offset and joins the session.
Staying in syncEvery ten seconds the client compares its position with the server's. A drift over three seconds is corrected with a seek; anything smaller is left alone, because ads and buffering always cost a few seconds and constant seeking would break the song.
Song boundaries and the lineupThe next five songs are decided in advance, stored, and shown to listeners in that order. Ninety seconds before a song ends, one poll takes a lock and prepares the first of them. The advance itself is a single conditional update, so concurrent polls cannot advance twice.
A song that will not embedAn upload with embedding disabled fails for every listener at once. Clients report it; after three distinct reports the song leaves the schedule. The catalogue file itself is never edited by the server.
Scheduling

First come, first served, plus weights

The base score is minutes waited, which alone is first come, first served. Conditions add to it, so a later request can be scheduled earlier. Waiting time keeps accruing, so every request is eventually played. Requests enter the published lineup from the second slot; the first slot is locked. The weights live in a table, not in code, and every scheduling decision records the winning score, so the weights can be re-tuned from what actually happened.

AI DJ

Scripts from the catalogue, two voices, two languages

The DJ speaks over the intro of every song while the music is ducked. For a request with a story, a language model reconstructs the story in two or three sentences and names the requested song; the song's note is not read. For a request without a story, and for catalogue songs, the note already in the catalogue is read as it is, with no model call. Every few catalogue songs the model adds a longer script with the time of day. Scripts are produced in Korean and English in one call, and each listener hears the language of their interface. Listeners who prefer music only switch the DJ off on their device.

Nothing outside the catalogueThe model sees only the fields the catalogue holds for that song: performer, writers, the note on what it is about, and the source line. It is instructed to state nothing beyond them, and the server strips anything that looks like a number, a link or a name that was not in the input.
Stories are reconstructed, not readA story is classified on arrival as safe, needs review, or rejected. When the song plays, the DJ paraphrases it in two or three sentences; the original text stays on the sender's own screen and is deleted thirty days after airing. The song still plays even when the review is late.
Two voices, one scriptThe listener picks a female or male DJ on their device. The script is generated once, in both languages, and written without first-person references, so either voice can read it. When generation fails, the song's note is shown as a caption instead, and playback continues.

Limits

What this does not claim

Shared listening over embedded video has hard edges. Below is where they are.

Not a music serviceNo rights are held and no audio is served. Each listener plays a YouTube upload through the official embed player; availability, ads and quality are YouTube's. A song whose upload disappears leaves the schedule with it.
Sync is approximateListeners are within a few seconds of each other, not sample-aligned. Ads insert time for one listener and not another; the next poll pulls them back. The target is the same song within a few seconds.
The DJ knows only the catalogueScripts are generated from the song's own fields and the story. They contain no facts beyond that input, and when generation fails the note is shown as a caption. The DJ does not answer questions or add facts.
One person's catalogue, anonymous listenersThe default schedule is a personal selection, not a chart. Requests are anonymous; a name to be called by is chosen by the sender and is not an identity. The listener count is a hashed-address heartbeat, not a login.
The offline app is a personal accessoryThe Android app reads the same catalogue from files on one device and plays without a network. It is sideloaded, not distributed, and it is not part of the shared session.
Open Music Play No install, no sign-up. When a session is on, one tap joins.
