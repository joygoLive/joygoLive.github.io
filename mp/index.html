MP · MyPlay

A radio everyone hears together.

One server clock, one schedule. Everyone connected hears the same song at the same point. Send a request with a story and it goes on air in the next slots; an AI DJ reads the story over the intro. When no one has requested anything, a hand-curated catalogue keeps the station running.

Open the station What this does not claim

No audio is served. Each listener's browser opens its own YouTube embed of the current song. The server holds only the clock and the schedule, and tells each client where the song is right now.

Premise

A playlist has no reason to come back to. A broadcast does.

MyPlay began as a personal catalogue player: one JSON file with credits and a note per song, served to an offline app and a web app. A player like that is complete on the first visit. A broadcast exists only at this moment, and a request puts the listener in it. The catalogue did not change; what changed is who holds the clock.

One clock, on the serverA single station row records the current song and when it started. Clients read it and seek to the same point. There is no audio stream to synchronise, only a timestamp.
The catalogue is the default scheduleWhen the request queue is empty the station picks from the catalogue: recent songs and the previous artist are avoided, songs whose embed is blocked are excluded. The station never goes silent for lack of requests.
Requests and stories are the inputA request is a song plus an optional story and an optional name to be called by. It enters the schedule from the next slot. A request with a story outranks one without; the DJ reads a reconstruction of the story, never the original text.
How it works

Advance on read, no cron

The hosting has no scheduler, so the clock advances when it is read. Every listener polls the station every ten seconds; whichever poll finds the song finished moves the station to the next one, and only one of them wins.

JoiningOne tap to start, because browsers do not play sound without a gesture. The client loads the current song at the server's offset and is in the broadcast.
Staying in syncEvery ten seconds the client compares its position with the server's. A drift over three seconds is corrected with a seek; anything smaller is left alone, because ads and buffering always cost a few seconds and constant seeking would break the song.
Song boundariesNinety seconds before a song ends, one poll takes a lock and decides the next song in advance. At the boundary the advance is a single conditional update, so concurrent polls cannot advance twice.
A song that will not embedAn upload with embedding disabled fails for every listener at once. Clients report it; after three distinct reports the song leaves the schedule. The catalogue file itself is never edited by the server.
Scheduling

First come, first served, plus weights

The base score is minutes waited, which alone is first come, first served. Conditions add to it, so a later request can go first. Waiting time keeps accruing, so nothing is starved. The weights live in a table, not in code, and every scheduling decision records the winning score, so the weights can be re-tuned from what actually happened.

AI DJ

A script from the catalogue, two voices, off if you want

The DJ is a language model called once per request song and once every few catalogue songs. It is given the song's credits, its note and its source, the time of day, and the story if there is one, and it returns one short script. The script is spoken over the song's intro while the music is ducked. Listeners who prefer music only switch it off on their device.

Nothing outside the catalogueThe model sees only the fields the catalogue holds for that song: performer, writers, the note on what it is about, and the source line. It is instructed to state nothing beyond them, and the server strips anything that looks like a number, a link or a name that was not in the input.
Stories are reconstructed, not readA story is classified on arrival as safe, needs review, or rejected. On air, the DJ paraphrases it in two or three sentences; the original text stays on the sender's own screen and is deleted thirty days after airing. The song still plays even when the review is late.
Two voices, one scriptThe listener picks a female or male DJ on their device. The script is generated once and written without first-person references, so either voice can read it. When generation fails, the song's note is shown as a caption instead, and the broadcast continues.

Limits

What this does not claim

A shared broadcast over embedded video has hard edges. Below is where they are.

Not a music serviceNo rights are held and no audio is served. Each listener plays a YouTube upload through the official embed player; availability, ads and quality are YouTube's. A song whose upload disappears leaves the schedule with it.
Sync is approximateListeners are within a few seconds of each other, not sample-aligned. Ads insert time for one listener and not another; the next poll pulls them back. Same song, roughly the same point, is the target.
The DJ knows only the catalogueScripts are generated from the song's own fields and the story. They contain no facts beyond that input, and when generation fails the note is shown as a caption. The DJ is not a source about music.
One person's catalogue, anonymous listenersThe default schedule is a personal selection, not a chart. Requests are anonymous; a name to be called by is chosen by the sender and is not an identity. The listener count is a hashed-address heartbeat, not a login.
The offline app is a personal accessoryThe Android app reads the same catalogue from files on one device and plays without a network. It is sideloaded, not distributed, and it is not part of the broadcast.
Open the station No install, no sign-up. If it is on air, one tap joins.
