WCP · Web Capability Probe

What your device actually gives the web.

Every capability is invoked in your own browser and the result recorded. Not a support table, not a feature-detection list, because declared support and actual execution frequently differ.

Premise

Declared support, working support

A capability table answers "is it in the spec". It cannot answer "does it work on this phone, in this browser, right now". Between the two sit the OS, the browser's own policy, the app hosting the WebView, and the response headers of the site itself.

Declaration present, execution failedThe API answers, the call fails. More dangerous than absence: code takes that path believing it works.
Same hardware, different answerOne device, four browsers, four results. The variable is not the silicon.
Our own response headers, recorded as absenceSharedArrayBuffer read as closed until COOP and COEP were added. The device was never the limit.
Scope

What it measures

Sensors, GPU and NPU, codecs, radios, storage, permissions, network, security context, and identity. Numbers where a number exists: GPU matrix multiply in GFLOPS, buffer ceilings in MB, refresh rate in Hz.

Execution, not enumerationEach item is invoked. A result is a return value or a thrown error, never a capability string.
Five states, not twoOpen · permission required · broken · absent · unmeasured. Collapsing these to yes/no loses the case that matters most.
A control groupThe same page is served twice, once with cross-origin isolation headers, to separate device limits from server configuration.
Nothing identifying is asked forNo account, no contact details. Device model, browser, and measurements only.

Method

Methodology

A figure is only as reliable as its methodology. This is the methodology, and it does not change when the figures do.

Four groups, not two

Open everywhere, permission everywhere, decided by the environment, closed everywhere. The third group is the interesting one: the hardware is not what decides.

Nine groups of checks

Radios, compute, motion, device, I/O, storage, camera, audio, location. Each item is invoked, and a result is a return value or a thrown error.

Engine builds actually measured

The UA engine token is frozen and uninformative (537.36, 605.1.15). What decides is the Chrome build or the OS build, so that is what gets recorded.

A ledger independent of sample size
—bands kept

History is stored per month × engine build × OS, not per device, so ten samples and ten thousand produce the same number of rows. Kept for five years by default.

Capabilities that flipped

Recorded when the same device and browser is measured twice and an item changes state. Browser updates open things, and occasionally close them.

Diagnosis

Five layers where a capability fails

"It does not work" is one sentence covering five different causes. Only the first is about the device.

1 · No hardwareThe part is not in the device. Nothing above can fix it.
2 · OS does not expose itPresent in hardware, absent from the platform API.
3 · Browser policyExposed by the OS, withheld by policy. Usually fingerprinting.
4 · Host app restricts itAn in-app WebView, narrower than the browser it is built on.
5 · Server response headersThe site's own response headers, blocking what the device could expose.

Wi-Fi belongs to none of the five. There is no Wi-Fi API in the web platform to refuse in the first place, so the question of which layer blocks it never arises. That is a different answer from "closed", and the tool reports it as such.

Limits

What this will not claim

A support list inflates the moment untested items are counted. Below is what the figures above do not claim.

The sample is smallMost of the sample is ours. Treat the numbers as a direction, not a population statistic.
A web app cannot see outside itselfRunning processes, installed apps, battery history, storage breakdown: all invisible from a page. Anything claiming otherwise from a browser is an estimate.
The native comparison is knowledge, not measurementNo native app was built to compare against, so that classification is documented rather than measured, and labelled as such.
Network readings are excluded from every scoreThey measure the line at that moment, not the device. A phone on good Wi-Fi would otherwise outrank a faster one.
Detected is not executedWhere a capability can only be checked for existence, never invoked, it is recorded as detected and labelled that way.
Numbers move between runsHeat, low-power mode, other load, charging state. A single reading is not a property of the device.
