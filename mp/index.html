MP · Music Play

Synchronised listening on one server clock.

A shared listening session over a curated catalogue. The server holds one clock and one schedule; every connected browser plays the same song from the same offset. Requests enter the published lineup with an optional story, an AI DJ reads a reconstruction of it over the intro, and the catalogue fills every slot the queue leaves empty.

Open Music Play What this does not claim

No audio path on the server. Nothing is streamed or proxied. Each client opens the official YouTube embed of the current song and seeks to the server's offset. What the server holds is a timestamp, a five-song lineup, and a script.

A service by joygoLive, built here and operated here. Beta.
Design

Three decisions that shape everything else

The service runs on a static catalogue file and a hosting platform with no scheduler and no persistent process. The architecture follows from those two constraints rather than from a media stack.

Clock, not streamOne state row holds the current song, its start time and its length. A client's position is start time plus elapsed time, computed in the browser. Synchronisation is a timestamp comparison; no audio leaves the server.
Advance on readThere is no cron. The state advances inside the poll that observes the song has ended, guarded by a conditional update so that concurrent polls advance it exactly once. Ninety seconds ahead, one poll takes a lock and prepares the next song's script and voice.
Catalogue as the fallback scheduleWhen the request queue is empty the server draws from the catalogue: songs never aired first, the most recently aired 60% excluded, the previous artist avoided, embed-blocked uploads excluded. The session does not run out of music.
Client

Join, stay in sync, hand over

The client is a single HTML file with no build step. It polls the server every ten seconds and does four things with the answer.

JoiningOne tap starts the session, because browsers refuse audio without a gesture. The same tap unlocks the voice player, so phones keep speaking on later songs. The client then loads the current song at the server's offset.
Staying in syncEach poll compares local position with the server's. Drift beyond three seconds is corrected with a seek; smaller drift is left alone, because ads and buffering cost a few seconds and constant seeking breaks the song.
Song boundariesThe next five songs are fixed in advance and shown in order. Slot one is locked; requests enter from slot two. A client that sees a new song loads it and, within the first 25 seconds, plays the DJ line over the intro with the music ducked.
Embed failuresAn upload with embedding disabled fails for every listener at once. Clients report it; after three distinct reports the song leaves the schedule. The catalogue file itself is never modified by the server.
Scheduling

A weighted queue over first come, first served

The base score is minutes waited, which on its own is first come, first served. Conditions add to it, so a later request can be scheduled earlier; waiting time keeps accruing, so every request is eventually played. The weights are read from a table at scheduling time, and every decision records its winning score. An operator pin overrides the order for one song.

Requests

Three input forms, one resolution path

A request is a song plus an optional story and an optional name to be called by. Whatever form the song arrives in, it is resolved to an embeddable video before it can enter the lineup, and the requester never picks the video.

Catalogue songChosen from the search box. The video is already known, so the request goes straight into the queue.
YouTube linkThe video is verified through oEmbed; an upload with embedding disabled is refused at submission. Title and length come from oEmbed and, where available, MusicBrainz.
Title and artist onlyCandidates come from the YouTube Data API, restricted to official artist channels, label and VEVO channels, and auto-generated Topic channels; fan uploads are excluded. MusicBrainz supplies the canonical length and candidates outside ±10 s are dropped. A model picks among the survivors; low confidence goes to the operator, not the lineup.
Two-stage story screeningA regular-expression pass rejects contact details and account numbers before anything else runs. What passes is classified by a model as safe, review or reject. Review holds the story until an operator approves it; the song plays regardless. Submissions are anonymous and rate-limited per address: twenty a day, five with a story, three waiting at once.
Requested songs stay separateSongs outside the catalogue live in their own table with the channel, its type and the reason for the pick. They play only when requested and never enter the shuffle. Promotion into the catalogue is an editorial step, not an automatic one.
AI DJ

One script, two voices, two languages

The DJ speaks over the first seconds of a song while the music is ducked. The script is generated in Korean and English in one call, and every listener hears the language of their interface. The voice is synthesised on the server and cached, so every listener hears the same take. Listeners who prefer music alone switch the DJ off on their device.

What gets a model callA request with an approved story: the model reconstructs it in two or three sentences and names the song; the catalogue note is not read. A request without a story: a fixed template naming the sender and the song. A catalogue song: the note as written, with a model-written script every fifth song. The greeting with the time and the DJ's name appears once per three-hour block.
Bounded inputThe model sees only the catalogue fields for that song and the story text. Story text is passed as data; instruction-like content is flagged rather than followed. Output containing contact-detail or link patterns is discarded and the template goes out instead.
VoicesTwo voices, Sulafat and Orus, from Google Cloud Text-to-Speech (Chirp 3 HD). The operator fixes one or lets them alternate every three hours; listeners do not choose. Audio is cached by text and voice, so a catalogue note is synthesised once. When synthesis is unavailable the browser's own speech engine reads the same script.
Operator viewEvery story, its verdict and the line the DJ actually spoke are shown in the admin console next to the request. Stories are retained until the operator deletes them, singly or in bulk; nothing is deleted on a timer.

Operations

Free tier by construction

The service is built to stay inside free tiers, and the guard is code rather than intention. Every external call is metered, thresholds alert, and the paid path is cut before the limit is reached.

MeteredSpeech characters, YouTube API units, storage reads and writes, function requests and model spend are counted per day or per month in the same database that holds the schedule. Alerts go out at 70, 90 and 100 per cent of each limit.
Cut-off, then fallbackAt 100 per cent the paid call is refused. Scripts fall back to an open-weight model on Workers AI, voices to a lighter synthesiser and then to the browser, stories to operator review. Playback depends on none of them.
Shared-account visibilityThe admin console lists every internal endpoint and external service with call counts for today, this month and since launch. Function requests and the database are shared with the rest of joygoLive, so a runaway here would be visible there.
Limits

What this does not claim

Shared listening over embedded video has hard edges. Below is where they are.

Not a music serviceNo rights are held and no audio is served. Each listener plays a YouTube upload through the official embed player; availability, ads and quality are YouTube's. A song whose upload disappears leaves the schedule with it.
Sync is approximateListeners are within a few seconds of each other, not sample-aligned. An ad inserts time for one listener and not another; the next poll pulls them back. The target is the same song within a few seconds.
The DJ knows only the catalogueScripts are generated from the song's own fields and the story. They contain no facts beyond that input, and when generation fails a template or the note goes out instead. The DJ does not answer questions or add facts.
A curated catalogue, anonymous listenersThe default schedule is an editorial selection, not a chart. Requests are anonymous; the name to be called by is chosen by the sender and is not an identity. The listener count is a hashed-address heartbeat, not a login.
Off air is a personal playerWhen no session is on, the same catalogue plays individually in the browser. The Android app reads the same catalogue from local files without a network; it is sideloaded, not distributed, and not part of the session.
Open Music Play No install, no sign-up. When a session is on, one tap joins.
